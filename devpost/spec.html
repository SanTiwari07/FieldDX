How this works, in plain language

Two halves, one rule file, one findings list

  • The engine (Python, FastAPI) reads the shipped Niphad data, checks whether a drop is real and unusual, scores the causes and picks the next check. Plain rules, no language model: the same field always gives the same answer.
  • The screens (React, TypeScript) show the case and let the officer record what they found.
  • The check list (data/checks.json) says what each result supports and what it counts against. The evidence rules live here, not in code.
  • The findings store (a SQLite file) keeps every finding, in order.

Opening a case rebuilds it from the satellite evidence, then replays each finding on top. Each finding moves only the causes the check list names. The next check is picked again from the causes still live. A fixed template writes the summary, so the wording is identical every run.

    Data model and failure modes

    Where each piece of data lives

    Data
    • Satellite evidence, fields, weather, scenes: shipped files in data/areas/niphad/. Read-only. Built
    • Check list: data/checks.json. Read-only at run time, edited once in this build. Change
    • Findings: rows in case_findings. Added on save. They persist across reloads and restarts until reset. New
    • The case on screen: not stored. It is rebuilt on every request from shipped data plus findings, so leaving and coming back shows the same case. Built
    • Update record: CaseResult.update, describing the latest finding. Replaces resolution. New
    Failure modes and fallbacks
    • Findings left from a previous take: the case opens already updated. Run reset_demo.py first.
    • A Gemini key in .env: updated cases still use the template, and FIELDDX_LLM=off covers the first summary too.
    • Engine output drifts from the video script: test_field128_demo.py fails before recording.
    • Existing tests expect closing: rewritten in the same build step.
    What was simplified, and why
    • No closing at all, instead of a four-outcome workflow. The proof is the feedback loop.
    • Template summary, instead of Gemini, so every run reads the same.
    • Fix the check list, instead of special rules in code. One data edit applies everywhere.
    • Shared demo officer, one area.
    • None fits = every cause ruled out. Simple and testable.
    Decisions and open issues

    Decided in this interview

    • A working drip line or moist soil counts only against irrigation failure. The rule lives in the check list.
    • The computed next check stands. Field 128 starts at the leaf undersides. No location-priority rule.
    • The demo records Leaves clean. Pest less likely; irrigation unchanged but first, never more likely; next check, the drip line.
    • Template summary for the proof and the video. Gemini stays optional for later.
    • Local only, with a one-command reset and a Field 128 test before filming.
    The useful unknown: how one rule change ripples

    Correcting one supports list changed Field 128's first check from the drip line to the leaf undersides. A looser scoring rule, where an against result also counts as separating, picked leaf yellowing first, because it treated "not pests" as evidence for irrigation. So the app's strict rule stays, and the Field 128 test now pins the behaviour down.

    PRD update and open issues

    The PRD's journey and payoff were revised to match: leaf undersides first, Leaves clean, then the drip line. Nothing is blocking. Check during the build that the phone dock and inbox read well with the new label.
