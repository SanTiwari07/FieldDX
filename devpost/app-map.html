How a finding becomes an updated investigation

A take-home guide to the proof of concept: the main pieces, one action traced through the real code, where to start a change, and one practice worth reusing.

The pieces

  • The engine (backend/app, Python and FastAPI) builds each case from the shipped Niphad satellite and weather data, scores the causes and picks the next check. Plain rules, so the same field always gives the same answer.
  • The check list (data/checks.json) says what each field result supports and what it counts against. The evidence rules live here.
  • The findings store (case_findings in SQLite, via backend/app/db.py) keeps every finding an officer records, in order.
  • The screens (frontend/src, React and TypeScript) show the case and the field checklist.

One action: recording Leaves clean on Field 128

Result on screen: Investigation updated · still open. Pest or disease spread is less likely (0.7 → 0.2). Irrigation failure is unchanged at 0.4 and now first. The slip moves to the drip line on the south edge.

The route through the code

A reference route: three stops, with real paths and search anchors.

  1. The officer saves a result. CloseCaseForm posts it with api.recordFinding, and saved sends the officer back to the case.
    frontend/src/components/NextCheck.tsx · search CloseCaseForm · frontend/src/pages/Checklist.tsx · search const saved
  2. The engine checks it, stores it, and rebuilds the case. record_finding refuses a check the case isn't waiting for, then add_finding saves the row. effective_case rebuilds from shipped data and replays every finding in order.
    backend/app/main.py · record_finding · backend/app/db.py · add_finding · backend/app/service.py · effective_case
  3. Only the named causes move, and the next check is chosen again. apply_finding adjusts the causes in the result's supports and against lists and nothing else. choose skips done checks, and _moves writes each cause's word label and reason.
    backend/app/resolve.py · apply_finding, _moves, _reason · backend/app/next_check.py · choose, split_score

A practice to reuse

Write the evidence rule down, then simulate it on the real case before you build. The spec set the rule that a working drip line counts only against irrigation failure. Simulating Field 128 under that rule showed something nobody had planned: the computed first check changed from the drip line to the leaf undersides, and the demo script had to change with it. Trying a looser scoring rule also showed it would treat "not pests" as evidence for irrigation, so the strict rule was kept.

Evidence: devpost/spec.md › Decisions and Open Issues (the useful unknown), pinned by test_before_any_finding_the_leaf_undersides_come_first in backend/tests/test_field128_demo.py.

On another project: whenever a rule decides what a user sees, write the rule down in plain words, run it on one real example before coding, and turn the expected output into a test. Surprises then show up in the plan, while they're still cheap to change.
